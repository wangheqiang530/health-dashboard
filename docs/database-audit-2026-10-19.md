# 数据库与全量导入完整性体检

审计时间：2026-10-19（Asia/Shanghai）

审计方式：只读查询生产 PostgreSQL、校验归档文件 SHA-256、扫描 Apple Health 主 XML、核对 Fitdays/iGPSPORT 全量归档与数据库记录。

## 结论摘要

**数据库引擎本身正常，归档文件完整；但 Apple Health ZIP 全量导入没有把全部原始记录结构化入库，当前不满足“所有数据即使暂未调用也要在数据库中保存原始值”的要求。**

- PostgreSQL 16.15 运行正常，当前数据库约 38 MB。
- `pg_dump` 全库导出测试成功。
- 20 个归档文件全部存在，文件大小与 SHA-256 均和数据库登记一致。
- Apple Health ZIP 压缩包完整，`unzip -t` 无错误。
- Fitdays 274 条记录、iGPSPORT 65 条骑行记录均已完整写入数据库，原始 JSON 与全量归档逐条深度比对无差异。
- Apple Health ZIP 含 1,749,650 条 `Record`、279 条 `Workout`、939 条 `ActivitySummary`、4 条 `Correlation`，但数据库没有对应的完整原始记录表。

## 1969 年日期来源

ZIP 内的 Apple Health XML 自身包含 4 条全零 `ActivitySummary`：

```text
1969-12-30
1969-12-31
2017-09-07
2017-09-08
```

前两条是明显的 Unix epoch 占位日期。它们没有任何健康记录，所有字段均为 0。

当前导入逻辑把 `ActivitySummary` 日期直接加入目标日期集合，因此生成了 4 个无有效信号的汇总日：

```text
1969-12-30
1969-12-31
2017-09-07
2017-09-08
```

因此界面显示的 `3268 天` 包含 4 个无效占位日；实际有步数等健康信号的日期为 `3264` 天。

这不是数据库损坏，也不是 3268 天记录被错误写入，而是导入器接受了 Apple Health 导出中的占位 `ActivitySummary`。

## 冲突覆盖与去重

### 正常部分

- `daily_summaries.day` 有主键，最新 ZIP 导入会覆盖同一天的汇总。
- `body_measurements (source_id, external_id)` 唯一，重复同步会更新字段。
- `cycling_activities (source_id, external_id)` 唯一，重复同步会更新字段。
- `health_metric_points.fingerprint` 唯一，完全相同的原始点不会重复插入。

### 风险部分

1. `health_metric_points` 使用 `ON CONFLICT DO NOTHING`，不是按自然时间键覆盖。未来同一指标同一时间出现修正值时，旧值可能保留并新增另一条，而不是以新导入覆盖。
2. `health_workouts` 没有自然键约束。最近 25 条训练记录实际只有 14 个不同训练，11 组记录因两次导入 JSON 对象键顺序不同而生成不同指纹，形成重复行。
3. ZIP 内 279 条训练记录中有 14 组同一开始时间的跨来源重复，例如 Strava 与 iGPSPORT 记录同一骑行。当前查询层会按来源和时间做部分去重，但底层仍保留重复。
4. Apple Health ZIP 导入的 3,259 天 `daily_summaries.hae_import_id` 为 `NULL`，没有导入批次溯源；ZIP 导入也没有写入 `hae_imports`。

## 精度检查

- Fitdays 与 iGPSPORT 的 `raw_record` 使用 JSONB 保存原始值，逐条深度比对一致。
- 结构化数值列使用 `NUMERIC`，没有发现负数或明显溢出。
- 体脂秤原始浮点与结构化列最大差异约 `0.000003`，属于显示/存储位数舍入，原始值仍完整保留。
- Apple Health ZIP 的每日汇总存在聚合与抽样精度损失；原始值目前只保留在 ZIP 中，不在 PostgreSQL 可查询表内。

## 归档与备份

- 20/20 个归档文件存在，大小与 SHA-256 全部一致。
- 归档文件与数据库索引一一对应，没有孤立文件或失效索引。
- 最近一次数据库冷备为 2026-10-19 03:15，早于本次 18:42 的全量 ZIP 导入；当前冷备不包含这次全量导入后的最新状态。
- `pg_dump` 现场一致性导出成功，说明当前数据库可以被完整备份。

## 风险等级

| 风险 | 等级 | 说明 |
| --- | --- | --- |
| 全量 Apple Health 原始记录未结构化入库 | P0 | 不满足“所有数据保存原始值”的核心要求 |
| 原始 ZIP 默认 365 天后删除 | P0 | 删除后无法恢复未结构化的 174 万条记录 |
| 1969/2017 全零占位日进入汇总 | P1 | 影响日期范围、日历与天数统计 |
| `health_workouts` 指纹去重不稳定 | P1 | 会产生重复训练行 |
| 指标冲突不是按新导入覆盖 | P1 | 不满足未来数据修正时的覆盖策略 |
| ZIP 导入缺少批次溯源 | P2 | 无法追踪某天来自哪次导入 |
| 体脂率/BMI/BMR 的 0 与缺失混用 | P2 | 可能影响图表与状态判断 |

## 建议修复顺序

1. 新增 Apple Health 原始记录表，逐条保存全部 `Record`、`Workout`、`ActivitySummary`、`Correlation` 及完整属性。
2. 导入完成后输出原始数、入库数、跳过数、解析失败数，并做事务内数量校验。
3. 过滤全零占位 `ActivitySummary`，或在导入报告中排除无信号日期。
4. 为训练与指标定义稳定自然键，按新导入时间覆盖，同时保留原始历史版本。
5. 原始健康数据归档默认不自动删除，或仅在确认全部原始记录已结构化入库后允许清理。
6. 为 ZIP 导入建立批次记录和来源文件关联。
